1. Агуулахын орлого, зарлага, үлдэгдлийг цаасан дээр тайлбар
================================================================================
📝 Тайлбар: L01 лабораторийн 1-р алхам. Энэ даалгавар нь агуулахын үндсэн ойлголтыг цаасан дээр бичиж тайлбарлахыг шаарддаг. Багш таны ойлголтыг шалгана. Энэ нь дараагийн бүх ажлын суурь болно.

Орлого = агуулахад бараа нэмэгдэх
📝 Тайлбар: Орлого гэдэг нь агуулахад шинэ бараа ирэх, нэмэгдэх үйлдэл. Жишээ нь: нийлүүлэгчээс 10 дэвтэр ирвэл энэ нь орлого болно. Үлдэгдэл нэмэгдэнэ. Орлого нь receipt буюу opening төрөлтэй байж болно.

Зарлага = агуулахаас бараа хасагдах
📝 Тайлбар: Зарлага гэдэг нь агуулахаас бараа гарах, хасагдах үйлдэл. Жишээ нь: хэрэглэгч 3 үзэг авбал энэ нь зарлага болно. Үлдэгдэл хасна. Зарлага нь issue төрөлтэй.

Үлдэгдэл = Өмнөх үлдэгдэл + Орлого — Зарлага
📝 Тайлбар: Энэ бол үлдэгдлийн тооцооны үндсэн томьёо. Өмнөх үлдэгдэл дээр орлогыг нэмж, зарлагыг хасна. Энэ томьёо нь бүх транзакцийн үндэс болно. Жишээ: 10 + 5 - 3 = 12.

Дүрэм: Үлдэгдэл 0-ээс бага болох ёсгүй.
📝 Тайлбар: Энэ бол бизнес дүрэм. Хэрэв 10 үлдэгдэлтэй байхад 11 зарлага хүсвэл систем татгалзах ёстой (409 алдаа). Энэ дүрэм нь сөрөг үлдэгдэл үүсэхээс хамгаална. Transaction rollback хийгдэнэ.

2. 5 барааны массиваас бага үлдэгдэлтэйг олох (JS ба Python)
================================================================================
📝 Тайлбар: L01 лабораторийн 2-р алхам. 5 барааны жагсаалтаас 10-аас бага үлдэгдэлтэйг олох даалгавар. JS болон Python хоёр хэлээр хийх ёстой. Энэ нь хоёр хэлний ижил төстэй байдал ба ялгааг ойлгоход тусална.

JavaScript:
const products = [
{ name: "Дэвтэр", stock: 25 },
{ name: "Үзэг", stock: 8 },
{ name: "Хавтас", stock: 3 },
{ name: "Маркер", stock: 15 },
{ name: "Цаас", stock: 2 }
];

const lowStock = products.filter(p => p.stock < 10);
📝 Тайлбар: JavaScript-ийн filter() функц нь массив дахь элементүүдийг шүүж, нөхцөл хангасан элементүүдийг буцаана. p.stock < 10 нөхцөл нь 10-аас бага үлдэгдэлтэй барааг шүүнэ. Үр дүн: Үзэг (8), Хавтас (3), Цаас (2). filter() нь шинэ массив буцаана, анхны массивыг өөрчлөхгүй.

Python:
products = [
{"name": "Дэвтэр", "stock": 25},
{"name": "Үзэг", "stock": 8},
{"name": "Хавтас", "stock": 3},
{"name": "Маркер", "stock": 15},
{"name": "Цаас", "stock": 2}
]

low_stock = [p for p in products if p["stock"] < 10]
📝 Тайлбар: Python-ийн list comprehension нь JS-ийн filter()-тай ижил үүрэгтэй. [p for p in products if p["stock"] < 10] нь 10-аас бага үлдэгдэлтэй барааг шүүнэ. Үр дүн JS-тэй ижил: Үзэг, Хавтас, Цаас. Python-д filter() функц бас бий, гэхдээ list comprehension илүү уншигдахуйц.

3. Хоёр хүснэгтийн холбоос бүхий SQL асуултын үр дүнг гараар таамаг
================================================================================
📝 Тайлбар: L01 лабораторийн 3-р алхам. SQL-ийн JOIN асуултын үр дүнг гараар таамаглах даалгавар. Энэ нь өгөгдлийн сангийн ойлголтыг шалгана. Гараар таамагласнаар та өгөгдлийн хамаарлыг ойлгоно.

SELECT p.name, w.name AS warehouse, sb.quantity
FROM stock_balances sb
JOIN products p ON p.id = sb.product_id
JOIN warehouses w ON w.id = sb.warehouse_id
WHERE sb.quantity < 10;
📝 Тайлбар: Энэ SQL асуулт нь 3 хүснэгтийг холбож байна: stock_balances (үлдэгдэл), products (бараа), warehouses (агуулах). WHERE sb.quantity < 10 нь 10-аас бага үлдэгдэлтэй барааг шүүнэ. Үр дүн: барааны нэр, агуулахын нэр, тоо хэмжээ. JOIN нь хоёр хүснэгтийн холбоосыг үүсгэнэ.

Гараар таамагласан үр дүн:

name	warehouse	quantity
Үзэг	Агуулах А	8
Хавтас	Агуулах А	3
Цаас	Агуулах Б	2

5. Одоогийн орлого, зарлага, тооллогын процессыг зур
================================================================================
📝 Тайлбар: L03 лабораторийн 2-р алхам. Одоогийн бизнес процессыг диаграм хэлбэрээр зурах даалгавар. Энэ нь системийн урсгалыг ойлгоход тусална. Процессын зураг нь шаардлага тодорхойлоход чухал.

[Нийлүүлэгч] → [Нярав: Орлого] → [Үлдэгдэл нэмэх]
↓
[Хэрэглэгч] ← [Нярав: Зарлага] ← [Үлдэгдэл шалгах]
↓
[Менежер: Тайлан харах]
📝 Тайлбар: Процессын диаграм. Нийлүүлэгчээс бараа ирж, нярав орлого бүртгэж, үлдэгдэл нэмэгдэнэ. Хэрэглэгч бараа авахад нярав зарлага бүртгэж, үлдэгдэл хасна. Менежер тайлан харна. Энэ урсгал нь системийн үндсэн үйл ажиллагааг харуулна.

Гурван асуудлыг шинжил
📝 Тайлбар: L03 лабораторийн 3-р алхам. Одоогийн системд байгаа 3 үндсэн асуудлыг шинжлэх даалгавар. Эдгээр нь шийдэл шаарддаг. Асуудал бүрд шийдэл санал болгоно.

Бүртгэл давхардсан → Давхар SKU-г хориглох
📝 Тайлбар: Асуудал: Нэг барааны SKU хоёр удаа бүртгэгдсэн. Шийдэл: Өгөгдлийн санд unique constraint тавьж, давхар SKU-г хориглоно. API нь 409 алдаа буцаана. Энэ нь өгөгдлийн бүрэн бүтэн байдлыг хангана.

Үлдэгдэл хүрээгүй → 409 алдаа, transaction rollback
📝 Тайлбар: Асуудал: 10 үлдэгдэлтэй байхад 11 зарлага хүссэн. Шийдэл: Систем 409 алдаа буцааж, transaction-ийг бүхэлд нь rollback хийнэ. Үлдэгдэл өөрчлөгдөхгүй. Энэ нь сөрөг үлдэгдэл үүсэхээс хамгаална.

Баримт засагдсан → Reversal механизм ашиглах
📝 Тайлбар: Асуудал: Posted баримтыг шууд зассан. Шийдэл: Reversal (буцаалт) механизм ашиглаж, эх баримтыг хэвээр үлдээж, шинэ буцаалтын бичилт үүсгэнэ. Аудит хадгалагдана. Энэ нь нягтлан бодох бүртгэлийн зарчимд нийцнэ.

docs/requirements.md файлд:
📝 Тайлбар: Энэ файлд бүх user story болон acceptance criteria-г бичнэ. Энэ нь шаардлагын баримт бичиг болно. AC (Acceptance Criteria) нь шалгаж болох нөхцөл байх ёстой.

## US-01: Бараа бүртгэх
**As a** нярав
**I want to** шинэ бараа бүртгэх
**So that** үлдэгдэл хянах боломжтой

📝 Тайлбар: User Story 01. Нярав шинэ бараа бүртгэх боломжтой байх ёстой. Энэ нь системийн үндсэн функц. Бараа бүртгэхгүйгээр орлого, зарлага хийх боломжгүй.

### Acceptance Criteria
- AC-01: Шинэ SKU-тэй бараа 201 буцаана
  📝 Тайлбар: Acceptance Criteria 01. Шинэ SKU-тэй бараа амжилттай бүртгэгдвэл HTTP 201 (Created) статус буцаана. Энэ нь амжилттай үйлдлийг илэрхийлнэ. 201 нь шинэ нөөц үүссэнийг илтгэнэ.
- AC-02: Давхар SKU 409 буцаана
  📝 Тайлбар: Acceptance Criteria 02. Хэрэв ижил SKU-тэй бараа дахин бүртгэх гэвэл HTTP 409 (Conflict) статус буцаана. Энэ нь давхардлаас хамгаална. 409 нь зөрчил илэрснийг илтгэнэ.
- AC-03: Хоосон нэр 422 буцаана
  📝 Тайлбар: Acceptance Criteria 03. Хэрэв барааны нэр хоосон байвал HTTP 422 (Unprocessable Entity) статус буцаана. Энэ нь validation алдааг илэрхийлнэ. 422 нь өгөгдөл буруу форматтайг илтгэнэ.

## US-02: Орлого бүртгэх
**As a** нярав
**I want to** орлогын баримт үүсгэх
**So that** үлдэгдэл нэмэгдэх

📝 Тайлбар: User Story 02. Нярав орлогын баримт үүсгэх боломжтой байх ёстой. Орлого нь үлдэгдэл нэмэгдүүлнэ. Орлого нь opening (эхний) эсвэл receipt (хүлээн авалт) байж болно.

### Acceptance Criteria
- AC-04: Opening 10 → үлдэгдэл 10
  📝 Тайлбар: Acceptance Criteria 04. Эхний үлдэгдэл (opening) 10 гэж бүртгэвэл үлдэгдэл 10 болно. Энэ нь эхлэлийн төлөв. Opening нь зөвхөн нэг удаа хийгдэнэ.
- AC-05: Receipt +5 → үлдэгдэл 15
  📝 Тайлбар: Acceptance Criteria 05. 10 үлдэгдэлтэй байхад 5 орлого нэмвэл үлдэгдэл 15 болно. Орлого нь нэмэгдлийг илэрхийлнэ. Receipt нь олон удаа хийгдэж болно.
- AC-06: Draft төлөвт үлдэгдэл өөрчлөгдөхгүй
  📝 Тайлбар: Acceptance Criteria 06. Баримт draft (ноорог) төлөвт байх үед үлдэгдэл өөрчлөгдөхгүй. Зөвхөн posted (батлагдсан) үед л нөлөөлнө. Draft нь засаж болно, posted нь засаж болохгүй.

## US-03: Зарлага бүртгэх
**As a** нярав
**I want to** зарлагын баримт үүсгэх
**So that** үлдэгдэл хасагдах

📝 Тайлбар: User Story 03. Нярав зарлагын баримт үүсгэх боломжтой байх ёстой. Зарлага нь үлдэгдэл хасагдана. Зарлага нь issue төрөлтэй.

### Acceptance Criteria
- AC-07: 10-аас 10 зарлага → үлдэгдэл 0
  📝 Тайлбар: Acceptance Criteria 07. 10 үлдэгдэлтэй байхад 10 зарлага хийвэл үлдэгдэл 0 болно. Энэ нь хил заагийн кейс. 0 үлдэгдэл нь зөв төлөв.
- AC-08: 10-аас 11 зарлага → 409, үлдэгдэл 10 хэвээр
  📝 Тайлбар: Acceptance Criteria 08. 10 үлдэгдэлтэй байхад 11 зарлага хүсвэл 409 алдаа буцааж, үлдэгдэл 10 хэвээр үлдэнэ. Энэ нь сөрөг үлдэгдэл үүсэхээс хамгаална. Transaction rollback хийнэ.
- AC-09: Сөрөг тоо 422 буцаана
  📝 Тайлбар: Acceptance Criteria 09. Хэрэв сөрөг тоо (-1) оруулбал 422 алдаа буцаана. Тоо хэмжээ үргэлж эерэг байх ёстой. 0 ч бас хориглоно.

## US-04: Үлдэгдэл харах
**As a** менежер
**I want to** үлдэгдлийн тайлан харах
**So that** шийдвэр гаргах

📝 Тайлбар: User Story 04. Менежер үлдэгдлийн тайлан харах боломжтой байх ёстой. Энэ нь шийдвэр гаргахад тусална. Тайлан нь шүүлттэй байх ёстой.

### Acceptance Criteria
- AC-10: Агуулахаар шүүх боломжтой
  📝 Тайлбар: Acceptance Criteria 10. Үлдэгдлийг агуулахаар шүүх боломжтой. Жишээ: Зөвхөн Агуулах А-ийн үлдэгдлийг харах. Энэ нь олон агуулахтай үед чухал.
- AC-11: Бараагаар шүүх боломжтой
  📝 Тайлбар: Acceptance Criteria 11. Үлдэгдлийг бараагаар шүүх боломжтой. Жишээ: Зөвхөн Үзэгний үлдэгдлийг харах. Энэ нь тодорхой барааны нөөцийг шалгахад тусална.
- AC-12: 0 үлдэгдэл харагдана
  📝 Тайлбар: Acceptance Criteria 12. 0 үлдэгдэлтэй бараа ч харагдах ёстой. Энэ нь дууссан барааг мэдэхэд тусална. 0 үлдэгдэл нь "дууссан" гэсэн үг биш, зүгээр л тоо.

## US-05: Баримт батлах
**As a** нярав
**I want to** draft баримтыг батлах
**So that** үлдэгдэлд нөлөөлөх

📝 Тайлбар: User Story 05. Нярав draft баримтыг батлах боломжтой байх ёстой. Батлалт нь үлдэгдэлд нөлөөлнө. Батлалт нь эцсийн үйлдэл.

### Acceptance Criteria
- AC-13: Posted баримт засах боломжгүй
  📝 Тайлбар: Acceptance Criteria 13. Posted (батлагдсан) баримтыг шууд засах боломжгүй. Зөвхөн reversal хийж болно. Энэ нь аудитын бүрэн бүтэн байдлыг хангана.
- AC-14: Давхар post 409 буцаана
  📝 Тайлбар: Acceptance Criteria 14. Нэг баримтыг хоёр удаа post хийх гэвэл 409 алдаа буцаана. Энэ нь давхар нөлөөллөөс хамгаална. Нэг post = нэг нөлөө.
- AC-15: Батлалт transaction-д хийгдэнэ
  📝 Тайлбар: Acceptance Criteria 15. Батлалт нь transaction дотор хийгдэнэ. Хэрэв алдаа гарвал бүх өөрчлөлт rollback хийнэ. Энэ нь өгөгдлийн бүрэн бүтэн байдлыг хангана.

## US-06: Буцаалт хийх
**As a** менежер
**I want to** posted баримтыг буцаах
**So that** алдаа засах

📝 Тайлбар: User Story 06. Менежер posted баримтыг буцаах боломжтой байх ёстой. Буцаалт нь алдаа засахад тусална. Буцаалт нь эх баримтыг хэвээр үлдээнэ.

### Acceptance Criteria
- AC-16: Бүтэн reversal хийгдэнэ
  📝 Тайлбар: Acceptance Criteria 16. Буцаалт нь бүтэн байх ёстой. Хэрэв 4 зарлага буцаах бол +4 нэмнэ. Хэсэгчилсэн буцаалт хийхгүй.
- AC-17: Дахин reversal татгалзана
  📝 Тайлбар: Acceptance Criteria 17. Нэг баримтыг хоёр удаа буцаах боломжгүй. Дахин буцаалт хийх гэвэл татгалзана. Энэ нь давхардлаас хамгаална.
- AC-18: Эх баримтын холбоос хадгалагдана
  📝 Тайлбар: Acceptance Criteria 18. Буцаалтын баримт нь эх баримттай холбогдсон байх ёстой. Энэ нь аудитад тусална. reversal_of талбар ашиглана.

## US-07: Хэрэглэгч нэвтрэх
**As a** хэрэглэгч
**I want to** системд нэвтрэх
**So that** эрхээрээ ажиллах

📝 Тайлбар: User Story 07. Хэрэглэгч системд нэвтрэх боломжтой байх ёстой. Нэвтрэлт нь эрхийн хяналтыг хангана. Token ашиглана.

### Acceptance Criteria
- AC-19: Token-гүй 401 буцаана
  📝 Тайлбар: Acceptance Criteria 19. Token-гүй хүсэлт явуулбал 401 (Unauthorized) алдаа буцаана. Энэ нь хамгаалалтыг хангана. 401 нь нэвтрээгүйг илтгэнэ.
- AC-20: Viewer write 403 буцаана
  📝 Тайлбар: Acceptance Criteria 20. Viewer эрхтэй хэрэглэгч бичих гэвэл 403 (Forbidden) алдаа буцаана. Зөвхөн унших эрхтэй. 403 нь эрх хүрэлцэхгүйг илтгэнэ.
- AC-21: Clerk зөв урсгал амжилттай
  📝 Тайлбар: Acceptance Criteria 21. Clerk эрхтэй хэрэглэгч зөв урсгалаар ажиллавал амжилттай болно. Бичих эрхтэй. Энэ нь үндсэн хэрэглэгчийн урсгал.

## US-08: Аудит харах
**As a** админ
**I want to** аудитын мөр харах
**So that** хэн юу хийснийг мэдэх

📝 Тайлбар: User Story 08. Админ аудитын мөр харах боломжтой байх ёстой. Энэ нь хэн юу хийснийг мэдэхэд тусална. Аудит нь бүх үйлдлийг бүртгэнэ.

### Acceptance Criteria
- AC-22: Actor, цаг, үйлдэл харагдана
  📝 Тайлбар: Acceptance Criteria 22. Аудит бичилтэд хэн (actor), хэзээ (цаг), юу (үйлдэл) хийсэн нь харагдана. Энэ нь мөрдөх боломжийг олгоно.
- AC-23: Password/token хадгалагдахгүй
  📝 Тайлбар: Acceptance Criteria 23. Аудит бичилтэд password эсвэл token хадгалагдахгүй. Энэ нь аюулгүй байдлыг хангана. Зөвхөн actor ID хадгална.
- AC-24: Шалтгаан бичигдэнэ
  📝 Тайлбар: Acceptance Criteria 24. Аудит бичилтэд үйлдлийн шалтгаан бичигдэнэ. Жишээ: "Алдаа засвар" гэх мэт. Энэ нь шийдвэрийн үндэслэлийг хадгална.
